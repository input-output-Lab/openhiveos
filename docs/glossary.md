# OpenHiveOS — Terminology Glossary

*This glossary is the single source of truth for all OpenHiveOS terminology. Every document, guide, PR description, and team conversation uses these terms exactly as defined here. Any document using a synonym for a term below must be corrected on sight. Terms marked **ARCH-006 locked** cannot be redefined without a new ADR.*

**Owner:** Clarence  
**Last updated:** 2026-05-20  
**Source authority:** ARCH-003, ARCH-005, ARCH-006, ARCH-007, ARCH-008  

---

## agents table

The PostgreSQL table that stores the agent registry for a Squad Instance. Each row represents one registered agent and holds the agent's slug, display name, token hash, token salt, grace-period rotation fields, `last_used_at`, `expires_at`, and `active` flag. The `agents` table is created in migration `001_init.sql` and is the authoritative source of which agents are permitted to use the Squad's MCP tools.

**See also:** Bearer Token, Server-Side Identity Resolution, Squad Instance  
**Source:** ARCH-008 §7, migration `001_init.sql`

---

## Agent OS *(ARCH-006 locked)*

The cognitive infrastructure layer — the runtime of memory, identity, SOPs, agent registry, token lifecycle, and coordination primitives — on which a Squad operates. It is not a feature set; it is the substrate beneath all features. The Agent OS has two tiers: OS Primitives (stable, deprecation-protected) and Coordination Utilities (active-development pace). OpenHiveOS is the open-source implementation of the Agent OS.

**Example:** The OpenHiveOS codebase, its PostgreSQL schema, and its MCP tool suite collectively constitute the Agent OS.  
**See also:** OS Primitive, Coordination Utility, Squad  
**Source:** ARCH-003, ARCH-006 Canonical Taxonomy

---

## Bearer Token

The credential that authenticates an agent process to its Squad Instance at boot time. In OpenHiveOS v0.1, the bearer token is the `AGENT_TOKEN` environment variable — a 97-character string in `<32-hex-salt>.<64-hex-secret>` format. The salt is embedded in the token so the server can compute the SHA-256 hash without a separate lookup. The plaintext secret never touches the database; only the hash is stored in the `agents` table. Tokens are generated by `scripts/provision-agent-token.ts`.

**See also:** Server-Side Identity Resolution, agents table  
**Source:** ARCH-001, ARCH-008 Decision 7

---

## Coordination Utility

A tool in the second tier of the Agent OS two-tier model. Coordination Utilities cover project and task management, sprint coordination, cron scheduling, and other active-development capabilities. Unlike OS Primitives, Coordination Utilities operate at an active-development pace — their APIs may change between sprints. Integrations connect to the Coordination Utilities tier only and are architecturally prohibited from accessing OS Primitives directly.

**Examples:** `create_task`, `query_projects`, `advance_sprint`, `create_cron`  
**See also:** OS Primitive, Integration  
**Source:** ARCH-003, ARCH-005

---

## Ed25519/TOFU

The peer-trust protocol used by Inter-Squad Bridges. Trust-on-First-Use (TOFU) means that when two Squad Instances communicate for the first time, each records the other's Ed25519 public key as trusted. Subsequent messages must be signed with the matching private key to be accepted. There is no central certificate authority — trust is established peer-to-peer at first contact. Ed25519 is selected for performance and key size characteristics. The protocol handles inter-Squad communication; it does not apply to agent-to-server auth within a Squad (which uses Bearer Tokens).

**See also:** Inter-Squad Bridge, openBridge  
**Source:** ARCH-004, ARCH-006

---

## Episodic Memory

A memory entry stored by the `store_memory` tool and retrieved by `search_memory`. Episodic memories are attached to a specific agent, task, or session context and capture what happened — observations, decisions, outcomes, and facts worth retaining across sessions. Stored as text plus a 768-dimension pgvector embedding (Gemini `embedding-001`) in the `memories` table. Episodic memories are OS Primitives tier data — stable, deprecation-protected, and scoped to the storing agent.

**See also:** OS Primitive, pgvector, agents table  
**Source:** ARCH-008, `src/db/queries/memory.ts`

---

## Integration *(ARCH-006 locked)*

Any system external to the Agent OS that consumes the Coordination Utilities tier to extend agent capabilities. Integrations are architecturally prohibited from accessing the OS Primitives tier directly (ARCH-005). They are not OS components — they are consumers. The boundary between Integration and Agent OS is enforced structurally: the ESLint `no-restricted-imports` rule blocks any `src/utilities/**` import from `src/primitives/**`.

**Examples:** openBridge (as an integration consumer of Utilities), nova-telegram-bridge, clickup-mcp-server  
**See also:** Coordination Utility, OS Primitive  
**Source:** ARCH-005, ARCH-006 Canonical Taxonomy

---

## Inter-Squad Bridge *(ARCH-006 locked)*

The communication channel between two Squad Instances. In the current architecture, this role is fulfilled by openBridge via Ed25519/TOFU. An Inter-Squad Bridge is not a shared database, not an internal message bus, and not an application-layer router. It is a peer-trust handshake layer that signs, verifies, and relays messages between independent Squad Instances. A bridge exists at the boundary between Squads — it never spans within a Squad.

**Example:** openBridge connecting an IO Labs Software Factory Squad Instance to an IO Labs Finance Squad Instance.  
**See also:** openBridge, Ed25519/TOFU, Squad Instance  
**Source:** ARCH-006 Canonical Taxonomy

## Managed Hive *(ARCH-006 locked)*

The Constitutional Ruling deployment mode in which IO Labs operates as both the Agent OS vendor and the Operator. IO Labs retains full visibility into agent thoughts, disposition profiles, and operational metrics. Slider ownership — the ability to tune agent behavioral parameters — remains with IO Labs. Managed Hive is the current production state of all IO Labs agents. It is distinct from Self-Hosted Deployment, in which the Operator operates their own Squad Instance without IO Labs runtime visibility.

**See also:** Operator, Self-Hosted Deployment  
**Source:** ARCH-006 Canonical Taxonomy, Constitutional Ruling (2026-04-18)

---

## MCP (Model Context Protocol)

The open standard protocol, published by Anthropic in 2024, over which AI agent clients (Claude, Cursor, GitHub Copilot) invoke OpenHiveOS tools. An MCP server exposes named tools with JSON input schemas. Clients discover tools, call them with validated arguments, and receive structured responses. In OpenHiveOS v0.1, MCP is implemented exclusively over `StdioServerTransport` — the server communicates on stdin/stdout with no HTTP surface. HTTP/SSE transport is a Sprint 4+ requirement.

**See also:** OS Primitive, Coordination Utility  
**Source:** ARCH-008 Decision 1

---

## openBridge

The IO Labs inter-agent messaging layer that connects Squad Instances. openBridge is the current implementation of the Inter-Squad Bridge role. It implements Ed25519/TOFU peer trust: each Squad Instance registers its public key with openBridge, and messages between Squads are signed and verified. openBridge is an Integration — it consumes the Coordination Utilities tier of each connected Squad. It is not a shared database and does not provide shared memory across Squads.

**See also:** Inter-Squad Bridge, Ed25519/TOFU, Integration  
**Source:** ARCH-004, ARCH-006

---

## Operator *(ARCH-006 locked)*

The entity that deploys, configures, manages, and owns one or more Squad Instances. The Operator owns the disposition profile post-deployment (Constitutional Ruling, 2026-04-18). IO Labs is simultaneously an Operator (for its own Squads under Managed Hive) and the Agent OS vendor (for external Operators under Embedded and Air-Gapped deployment modes). The Operator provisions bearer tokens, manages database credentials, and controls the agent registry.

**Examples:** IO Labs (Managed Hive Operator). A marketing agency (Embedded Operator). A school district (Air-Gapped Operator).  
**See also:** Managed Hive, Self-Hosted Deployment, Squad Instance  
**Source:** ARCH-006 Canonical Taxonomy

## OS Primitive

A tool in the first tier of the Agent OS two-tier model. OS Primitives are the stable, deprecation-protected core tools that every agent depends on for memory, reasoning, and identity. Once an OS Primitive ships to production, its tool name and input schema are frozen — breaking changes require a new primitive name, not a modification. The eight OS Primitives in OpenHiveOS v0.1 are: `store_memory`, `search_memory`, `store_thought`, `ratify_thought`, `query_thoughts`, `set_disposition`, `get_disposition`, `search_sops`.

**See also:** Coordination Utility, Agent OS  
**Source:** ARCH-003, ARCH-005, ARCH-008

---

## pgvector

The PostgreSQL extension that enables vector storage and cosine-similarity semantic search within the OpenHiveOS database. Used by `search_memory`, `search_sops`, and thought retrieval to find semantically similar content without keyword matching. OpenHiveOS uses 768-dimension vectors, generated by the Gemini `gemini-embedding-001` model. The pgvector `<=>` operator computes cosine distance; results are ranked by `1 - (embedding <=> query_vector)` as a similarity score between 0 and 1.

**See also:** Episodic Memory, SOP Entry  
**Source:** ARCH-002, ARCH-008, `src/db/queries/`

## Selective Extraction

The codebase strategy adopted in ARCH-007 (8/8 unanimous). OpenHiveOS starts from a clean, empty scaffold — not a fork or copy of the OpenSquad MCP Server codebase. Primitives are extracted one at a time from the production OpenSquad MCP Server, each extraction reviewed by Locksmith before merging to main. No git history from the source repository is inherited. No production credentials, tokens, or IO Labs internal references appear in the OpenHiveOS repository at any point.

**See also:** OS Primitive  
**Source:** ARCH-007

## Self-Hosted Deployment *(ARCH-006 locked)*

A deployment mode in which the Operator downloads and operates the Squad Instance on their own infrastructure. IO Labs ships the Docker Compose artifact; the Operator runs it. IO Labs has no runtime visibility into agent thoughts, memories, or operational metrics unless the Operator explicitly opts into Managed Hive. Includes both Embedded (limited IO Labs configuration access) and Air-Gapped (zero IO Labs network path) modes from the Constitutional Ruling.

**Example:** A school operating a Squad Instance on school-owned servers, with student data never leaving school premises.  
**See also:** Managed Hive, Operator, Squad Instance  
**Source:** ARCH-006 Canonical Taxonomy

---

## Server-Side Identity Resolution *(ARCH-001 locked)*

The architectural principle that agent identity — who is making a tool call — is resolved exclusively by the server from the bearer token. The caller cannot supply their own `agent_name` field and have the server trust it. The server resolves the agent slug at boot by verifying `AGENT_TOKEN` against the `agents` table, then closes the resolved slug over all tool handler registrations. Every write primitive stamps the server-resolved slug on the stored record, not any value from the tool call payload.

**See also:** Bearer Token, agents table  
**Source:** ARCH-001, ARCH-008 Decision 7

---

## SOP Entry

A Standard Operating Procedure entry stored in the `sops` table. SOP entries represent the documented "Way" the team operates — process steps, behavioral guidelines, and operational standards that agents can retrieve by semantic similarity via `search_sops`. Each SOP entry has a category, optional agent scope, instruction text, source path reference, and a 768-dimension pgvector embedding. SOP entries are OS Primitives tier data.

**See also:** OS Primitive, pgvector, Episodic Memory  
**Source:** ARCH-008, `src/db/queries/sops.ts`

---

## Squad *(ARCH-006 locked)*

One complete, physically isolated deployment of the Agent OS, serving a defined set of agents and use cases for one Operator. The Squad is the atomic deployment unit and the atomic product unit. A Squad has its own PostgreSQL database, its own MCP server process, its own `agents` table, its own bearer tokens, its own migrations, and its own data. Squads share no infrastructure by default. The phrase "one Squad" means one Docker Compose stack — everything the stack contains is the Squad.

**Example:** IO Labs Software Factory Squad. IO Labs Finance Squad. A marketing agency's Client A Squad.  
**See also:** Squad Instance, Operator, Agent OS  
**Source:** ARCH-006 Canonical Taxonomy

---

## Squad Instance *(ARCH-006 locked)*

A running deployment of a Squad — the specific, live combination of Agent OS runtime, PostgreSQL database, bearer token authority, and agent registry currently serving traffic. One Squad has exactly one Squad Instance at a given time. The Squad Instance is what the Operator provisions, monitors, upgrades, and decommissions. The Squad Instance exposes a `GET /health` endpoint (HEALTH_PORT) for Docker health checks and a stdio MCP interface for agent tool calls.

**Example:** The Docker Compose stack running on port 3010 with database `openhiveos_finance`, serving IO Labs Finance agents under their provisioned bearer tokens.  
**See also:** Squad, Operator, agents table  
**Source:** ARCH-006 Canonical Taxonomy, ARCH-008
